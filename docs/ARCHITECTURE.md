## 1. Goal

A reproducible PostgreSQL database, shipped via Docker, that contains:

1. Every Federal Supreme Court (BGer) ruling **decided 2025-10-01 … 2026-06-30** (all divisions, ~6,000 rulings), with metadata and full text.
2. The extra rulings outside that window for which we have a human summary (23 cases decided in Q3/2025).
3. Suva's **relevance labels** (from the xlsx) attached to rulings.
4. Suva's **gold summaries** (55 human-written DE + FR pairs) attached to rulings.
5. Room for later data: expert relevance overrides, edited summaries, model outputs.

Judges will **not** re-run the scraping. They start from a database dump. But they must be **able** to re-run the pipeline and get the same result.

## 2. Assumptions and decisions

Confirmed by the organiser (2026-11-27):

- **A1. Quarters are defined by decision date**, not publication date. The hold-out set was built the same way as the sample set. Q2/2026 = decided 2026-04-01 … 2026-06-30. "June 2026" = decided in June 2026.
- **A2. The cantonal row in the xlsx is a mistake.** Only Federal Supreme Court rulings count.
- **A3. Any open-source / open-use data source is allowed**, not only bger.ch.

Our own decisions:

- **A4.** The xlsx is a complete list of relevant rulings for Q4/2025 + Q1/2026 (stated in the brief). Every other ruling decided in those quarters is "not relevant". Rulings decided in Q2/2026 and Q3/2025 are "unknown".
- **A5.** We store all divisions, not only 8C/9C. All 59 labelled positives are in 8C/9C, but one example summary (4A_106/2025) is from a civil division, and experts must be able to summarise any ruling.
- **A6.** Nothing is discarded. Every source's record and text is kept; the canonical row records which source each value came from.
- **A7.** PostgreSQL 16 in Docker Compose (db container + app container later). Python 3.12 managed with uv. Plain SQL migrations, no ORM.
- **A8.** No firewall evasion. bger.ch is fetched sequentially, slowly, with an honest user agent, and the crawler stops on the first block.
- **A9.** Tests never touch the network. They run on small saved samples.
- **A10. Keep the source text of everything we take** (decided 2026-11-27). Every source's full text for a ruling is stored in `ruling_texts`, not only the canonical one. "Everything we take" means rulings in the window plus the extra gold-summary cases: from the Hugging Face file (~174,000 rulings) we load **only those rows**, never the whole file.
- **A11. Dependencies approved:** `psycopg[binary]`, `pyarrow` (runtime), `pytest` (dev). Anything else needs approval.
- **A12. The EDA notebook (`notebooks/`) is personal exploration and must not be pushed.** It is excluded locally via `.git/info/exclude`. Never `git add` it, and never use `git add -A` / `git add .` in this repo: add files by path.

### 3.3 bger.ch daily lists (already crawled: 2025-07-01 … 2026-06-30)

Existing code: `src/bger_news.py`. Cache: `data/cache/news/YYYYMMDD.html` (git-ignored).

- URL: `https://www.bger.ch/ext/eurospider/live/de/php/aza/http/index_aza.php?date=YYYYMMDD&lang=de&mode=news`
- One list per weekday; weekends return an empty body (1 byte). 261 lists, 7,769 unique rulings.
- Per ruling: decision date, case number, subject area (`<CITE>`), subject line (next table row), link to full text. The list's own date = publication date.
- **Publication star**: a `*` appended to the subject area inside `<CITE>`, e.g. `Invalidenversicherung*`.
- Quirks: page declares UTF-8 but is **cp1252**; the server omits its TLS intermediate certificate (we ship DigiCert's intermediate in `src/certs/`, verification stays on); a case can appear on more than one list (1 seen).
- **Firewall (Imperva)**: blocked after ~465 requests at 1 req/s; the block lasted over an hour. A block is HTTP 403 or a page containing "Incapsula". Block pages must never be cached.
- **Missing**: lists for 2026-07-01 … 2026-09-30 (66 weekdays). Needed because rulings decided in Q2 are published up to ~2 months later (median lag 22 days, max seen for relevant rulings 56).

### 3.5 entscheidsuche.ch

- `https://entscheidsuche.ch/docs/CH_BGer/` — one `.html` (full text) + one `.json` (metadata) per ruling. robots.txt allows crawling. No firewall seen.
- Filename: `CH_BGer_<NNN>_<docket with - for _ and />_<decision date>` e.g. `CH_BGer_008_8C-72-2025_2025-12-11.html`. `NNN` looked like the docket's first digit zero-padded (8C→008, 5A→005, 4A→004); **do not hard-code this**: resolve filenames from the directory listing.
- JSON fields seen: `Signatur`, `Sprache`, `Datum`, `Num`, `HTML.URL`, `HTML.Checksum`, `Scrapedate`.
- **Bulk search API (preferred, verified 2026-11-27):** `POST https://entscheidsuche.ch/_search.php` with an Elasticsearch query body. It returns full documents, including the text in `_source.attachment.content`. Example filter: `{"term":{"hierarchy":"CH_BGer"}}` + `{"range":{"date":{"gte":"2026-06-01","lte":"2026-06-30"}}}`. Fields: `id` (= filename stem), `date` (decision date), `reference` (list of case numbers), `language`, `title`, `hierarchy`, `scrapedate`, `attachment.content_url`. June 2026 returned 773 hits, the same count as Swiss Case Law.
- **Fetch plan:** one query per month of the window, paged with `size` ≤ 100 and `search_after`, sorted by `id` for a stable order; save each response page as a raw file. That is ~70 requests for the whole window instead of ~6,000 file downloads. Use per-file download only for single rulings (the extra gold-summary cases can also be queried by `reference`).
- To check in Phase 1: that `attachment.content` equals the text of the `.html` file for a sample.

## 4. Hierarchy of truth and source roles

**Hierarchy (decided 2026-11-27). When sources disagree, the higher tier wins:**

1. **bger.ch**: the official website (daily lists and ruling pages). Ground truth.
2. **entscheidsuche.ch**: the mirror.
3. **Swiss Case Law** (Hugging Face).

Rules:

- For each field, the canonical value is the value from the **highest tier that has a valid value**. "Valid" means it passed that field's checks (section 6.1). A higher tier with an invalid value (e.g. an error page) is skipped, not trusted.
- A lower tier never overwrites a higher tier. Re-running with new data from a higher tier upgrades the canonical value and records the change.
- Every disagreement between tiers is written to `conflicts` (section 5.2), whichever side wins.
- `field_sources` on each ruling records the tier each value came from, so "how much of this dataset is tier 1?" is a query.
- Fields that only exist in tier 3 because a third party extracted them (`outcome`, `cited_decisions`, statute references) are marked **derived**. They are hints, not facts.

What each tier can actually supply:

| Field | Tier 1: bger.ch | Tier 2: entscheidsuche | Tier 3: Swiss Case Law |
|---|---|---|---|
| Ruling exists (index) | lists (blocked beyond 2026-06-30 for now) | directory listing | yes, complete for the window |
| Case number, decision date | lists | filename + JSON | yes |
| **Publication date** | **lists: only reliable source** | no | 24 % filled (fallback only) |
| **Publication star** | **lists: only source** | no | 11 % filled, unreliable: never used |
| Subject area, subject line | lists | no | `legal_area` 71 %, `title` 99 % |
| Language, division | ruling page | JSON | yes |
| Full text | ruling page (firewall: single rulings only) | yes | yes (3 known error pages) |
| Outcome, cited rulings, statutes | no | no | yes (derived) |

Consequences:

- **Publication date and star** come from the bger.ch lists. A ruling that has not appeared on a crawled list has `publication_date = NULL` and `starred = NULL` ("not known"), never `false`. `starred = false` means "seen on a list without a star". Until the 2026-07 … 2026-09 lists are fetched, rulings published after 2026-06-30 stay NULL; for those, tier 3's `publication_date` is used when present and tagged as tier 3.
- **Full text**: canonical = bger.ch page if we have it, else entscheidsuche, else Swiss Case Law. Because bulk fetching bger.ch is not possible, in practice most canonical texts come from tier 2, cross-checked against tier 3 by hash.
- **Tier-1 text for the rulings that matter most**: once bger.ch is reachable, fetch the ruling page for the labelled and gold-summary cases (82 rulings, far below the firewall threshold).

## 5. Data model (PostgreSQL)

### 5.1 Identity

- Canonical case number format: `8C_72/2025` (regex `^\d{1,2}[A-Z]_\d+/\d{4}$`).
- `rulings` primary key: surrogate `id`; unique on `(docket, decision_date)`.
- Labels and gold summaries only carry a case number. They attach by `docket`; if a docket ever matches more than one ruling, the loader fails loudly (U3).

### 5.2 Tables

```sql
-- provenance
ingest_runs(id, started_at, finished_at, command, params jsonb, git_commit, status)
raw_files(id, source, key, path, sha256, bytes, fetched_at, ingest_run_id)      -- unique(source, key)

-- one row per source record, nothing lost
source_records(id, source, source_key, docket, decision_date, record jsonb, raw_file_id, unique(source, source_key))
--   source ∈ {'bger_list','swiss_caselaw','entscheidsuche','bger_ruling'}

-- canonical
rulings(
  id, docket, decision_date, division, language,
  publication_date, starred,                -- from bger lists; NULL if not (yet) listed
  area, subject,
  outcome, cited_decisions jsonb,           -- derived (third party)
  official_url,
  field_sources jsonb,                      -- {"area":"bger_list","outcome":"swiss_caselaw",…}
  flags jsonb,                              -- {"text_mismatch":true,"missing_in":"swiss_caselaw",…}
  in_window boolean, created_at, updated_at,
  unique(docket, decision_date))

ruling_texts(id, ruling_id, source, text, sha256_normalized, char_count, is_canonical, unique(ruling_id, source))

statute_refs(ruling_id, law_code, article, paragraph, mention_count)   -- from graph/statute_references.parquet (optional)

-- every cross-source disagreement, and every rejected value
conflicts(id, ruling_id, field, winner_source, loser_source, winner_value, loser_value, kind, detected_at)
--   kind ∈ {'value_mismatch','text_mismatch','bad_text','duplicate_collapsed','missing_in_source'}

-- labels: append-only, several label sets can coexist
labels(id, ruling_id, label_set, value, quarter, metadata jsonb, created_by, created_at)
--   label_set = 'suva_xlsx_2025Q4_2026Q1', value = 'relevant'
--   metadata  = {"erstellt": "...", "sharepoint_url": "...", "xlsx_title": "...", "xlsx_row": 12}
--   later: label_set = 'expert_override', value ∈ {'relevant','not_relevant'}

-- gold summaries: versioned
gold_summaries(id, ruling_id, language, title, body, author, source_file, version, is_current, created_by, created_at,
               unique(ruling_id, language, version))
```

### 5.3 Derived view

```sql
v_relevance(ruling_id, docket, decision_quarter, relevance, basis)
--   'relevant'      : has a 'relevant' label (xlsx), or has a gold summary (basis = 'gold_summary_only' for the 23 Q3 cases)
--   'not_relevant'  : decided 2025-10-01 … 2026-03-31 and no relevant label   (A4)
--   'unknown'       : everything else (Q2/2026 = prediction target, Q3/2025 without summary)
```

`not_relevant` is never stored, only derived, so a later label change needs no clean-up.

## 6. Pipeline

```
fetch      → data/raw/…            (immutable files + sha256 in a manifest)
load       → source_records, ruling_texts (per source)
reconcile  → rulings (field precedence from section 4, flags)
attach     → labels (xlsx), gold_summaries (HTML)
verify     → counts, hashes, invariants
dump       → db/init/*.sql.gz      (what judges load)
```

Rules:

- **Every step is idempotent** (upserts keyed on natural keys). Running twice changes nothing.
- **fetch is the only step that touches the network.** Everything after it runs offline from `data/raw/`.
- **Window filter** lives in one config value: `DECISION_FROM=2025-10-01`, `DECISION_TO=2026-06-30`, plus "extra dockets" = the gold-summary cases.
- **Bad-text check** (applies to every source): a text is rejected if it is shorter than 600 characters, contains "Dokument nicht gefunden" / "nicht verfügbar", or has no court signature block in its last 400 characters. A rejected text is still stored (flagged `bad_text`), never chosen as canonical, and triggers the next source in the fallback chain.
- **Duplicates**: collapse rows with the same `(docket, decision_date)` and identical normalised text; keep the `decision_id` without the `-D` suffix as `source_key`.
- **Text comparison**: normalise (Unicode NFC, collapse whitespace, strip) then sha256. Different hash across sources → `flags.text_mismatch`, keep both, canonical = highest valid tier (section 4); the mismatch goes to `conflicts`.
- **Never silently drop**: a ruling present in one source and missing in another is kept and flagged.

### 6.1 Data quality principles

1. **Raw data is immutable.** Fetched files are never edited. All cleaning happens downstream and is repeatable.
2. **Validate at the door.** Each source record is checked before it can become canonical: case-number format, parseable dates, decision date ≤ publication date, language ∈ {de, fr, it}, and the bad-text check above.
3. **Quarantine, never delete.** A rejected value is stored with its reason in `conflicts`; it just cannot be canonical.
4. **Every row is accounted for.** For each source and run: records read = loaded + collapsed as duplicates + rejected. `verify` fails if the numbers do not add up.
5. **Provenance for every value** (`field_sources`), and for every file (`raw_files.sha256`).
6. **Unknown is not false.** Missing values are NULL; nothing is defaulted.
7. **Constraints live in the database**: NOT NULL, UNIQUE, foreign keys, CHECK (e.g. label values, language codes). A bad write fails instead of being stored.
8. **Idempotent and deterministic.** Same inputs → same database, in any order of runs.
9. **Known defects are regression tests.** Fixtures must include: the 3 error-page texts, an exact duplicate (`-D` suffix), the real double ruling 7B_1356/2025, a cp1252 list page, a starred list entry, a firewall block page, the cantonal xlsx row, and the `458/2025` row.
10. **A data-quality report is produced by every build** (`data/quality_report.md`): counts per source, per tier and per field, conflicts by kind, rulings without publication date, texts without a second source.

### Invariants `verify` must check

- 59 `relevant` labels; 0 labels for the cantonal row; `8C_458/2025` labelled.
- 55 rulings with gold summaries, 110 summary rows (55 × DE/FR), none empty.
- Every labelled ruling and every gold-summary ruling has a canonical full text.
- No ruling in the window without text unless flagged.
- Label quarter equals decision-date quarter for all labels.
- Raw file hashes match the committed manifest.

## 7. Reproducibility

Two levels, both supported:

**Level 1: rebuild from the raw snapshot (exact, offline).**
We archive the raw inputs we used: the bger.ch list pages, the entscheidsuche files, and the **window subset** of the Swiss Case Law file (not the 925 MB original). `build` from this snapshot gives a byte-identical dump. This is the guarantee.

**Level 2: re-fetch from the internet (verified, best effort).**
Note: the bger.ch list pages cannot currently be re-fetched by a script (firewall). For that source, the archived pages in the raw snapshot are the only reproducible input; `fetch` reports them as "skipped: blocked" rather than failing.
`fetch` downloads everything again and compares each file's sha256 with `data/manifest.json`. It should match, because the Hugging Face revision is pinned and published rulings do not change. But we do not control the sources: the mirror may re-scrape a file, Hugging Face history can be rewritten, and bger.ch may block the crawler. Any difference is reported per file, not silently accepted.

Mechanics:

- `data/manifest.json` (committed): pinned Hugging Face revision; for every raw file: source, key, sha256, bytes, fetch date.
- Deterministic ordering everywhere (sort before insert and dump).
- `ingest_runs` records the git commit and parameters of every run.
- The raw snapshot is too large for git: published as a release asset with its own sha256 (see Q3).

## 11. Future feature — DO NOT BUILD YET

**Intent:** in the web app, an expert picks a date range and the system fetches and adds the rulings from that range to the dataset.

Planned shape:

```python
ingest(date_from, date_to, by="decision") -> IngestReport
```

1. bger.ch lists for the range (plus a look-ahead for the publication lag) → index, star, publication date. ~22 requests per month of range.
2. Full text from Swiss Case Law (daily delta files, a few MB per day).
3. Fallback: entscheidsuche.ch per ruling.
4. Fallback: bger.ch ruling page, slow, stop on block.
5. Reconcile + report (new, updated, flagged, missing).

**Design constraints to respect now** (so this is cheap later):

- Source adapters share one interface: `discover(date_from, date_to)` and `fetch_text(docket, decision_date)`.
- All writes are idempotent upserts; re-ingesting a range never duplicates.
- The window is a parameter, never a hard-coded constant inside adapters.
- `ingest_runs` exists from day one.
- Network errors and firewall blocks are reported as partial results, not crashes.

Not decided yet: how it runs from the UI (background job vs request), and how a "live" ingest relates to the pinned, reproducible dataset.
